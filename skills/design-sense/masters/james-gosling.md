# James Gosling

**Class:** master · **Head:** the substrate decides what's possible

NeWS (1986): the window system as a programmable medium — PostScript processes
running *in the server*, so interfaces were programs living next to the display
instead of protocols shouting across it. NeWS is the substrate HyperLook and
pie menus flourished on, and its death is the field's great counterfactual
(the X11 lesson: [worse-is-better](../methods/worse-is-better.md) wins substrate
wars). Gosling Emacs before that: Mocklisp and the screen-update algorithm that
made Emacs portable beyond ITS. Then Java: "write once, run anywhere" — the
network as the computer, the VM as the neutral ground. Three times the same
conviction: build the medium, and the applications follow.

## Votes

- **Put the program where the pixels are** — NeWS ran interface code in the
  display server; latency is a design material, so compute next to the glass
  ([Wikipedia: NeWS](https://en.wikipedia.org/wiki/NeWS))
- **Build the medium, not the app** — Emacs extensibility, NeWS programmability,
  the JVM: three substrates, each of which grew applications its author never
  imagined ([tourist-policy](../methods/tourist-policy.md) for platforms)
- **Make the extension language a real language** — Mocklisp's lesson (and
  HyperTalk's, and PostScript's): users will program more than you expect;
  don't give them a toy ([low-floor-no-ceiling](../methods/low-floor-no-ceiling.md))
- **Write once, run anywhere** — neutrality of substrate is a feature users feel
  as freedom
- **Study your losses** — the NeWS/X11 postmortem is required reading in
  [worse-is-better](../methods/worse-is-better.md); losing elegantly teaches
  more than winning accidentally

## Vetoes

- Don't put the intelligence on the wrong side of the wire
- Don't confuse the popular substrate with the capable one — but see worse-is-better before betting against popular
- Don't build the app when the medium is the leverage
